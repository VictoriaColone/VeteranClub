## 阅读与版本维护规则

本手册是个人维护用的“目前做了什么、入口在哪、改哪里”的总览。章节中的 **1.0.1** 是产品和功能文档版本，不是 Vue、Spring Boot、Flyway 或构建包的版本。

1. 未正式发布前，前端和后端都保持 **1.0.1**；修 UI、加接口、改数据库、推送 Git、部署验收都不自动升版本。
2. 日常改动更新本手册对应章节，并追加到文末的“1.0.1 开发记录”，记录日期、改动、影响和验证。不要为每次修改建立一个新版本。
3. 正式发布由项目所有者明确确认。届时将三份手册复制到 `docs/releases/1.0.1/`，登记发布日期、源码提交、构建模式和数据库迁移版本，保留为不可覆盖的版本快照。
4. 下一版本号由项目所有者确定。新版本保留独立章节或快照，已发布版本的功能说明不直接改写成新行为。
5. 当前 `package.json`、工作区依赖及 Maven 坐标仍有 `1.0.0` 工程包号；本次仅建立功能版本基线，不修改构建坐标或产物名称。这些工程包号不能用来判断是否正式发布。

本手册按实际源码整理。旧 README、演示说明与早期 API 文档中出现的“快速邀请”“发现页＋号”“接单过滤”“员工 TOTP 登录”等历史描述，不代表当前页面。

“老板”“打手”是业务身份，不是两个独立登录系统。后端普通用户统一为 `role=user`；是否能发布/接单由 `approved` 和具体的 `qualificationGames` 决定。

| UI | 纯老板，无有效入驻项目 | 已入驻成员，至少一个有效游戏×类型 |
|---|---|---|
| 发现、购买服务 | 有 | 有；不能购买自己的商品 |
| 接单底部 tab | 隐藏 | 显示 |
| 我的页子 tab | 不显示，直接展示订单内容 | “我的订单 / 我的商品” |
| 订单归属切换 | 整块隐藏；按全部本人可见订单展示 | 全部订单 / 我下单的 / 我参与的 / 派给我的 |
| 我的商品、发布商品 | 无 | 有；只可发布已通过考核的游戏和类型 |
| 接单状态开关 | 无 | 用户名称右侧：“接单中 / 服务中” |
| 我要入驻 | 下方功能菜单 | 下方功能菜单，可继续申请其他游戏/类型 |
| 帮助与客服 | 下方功能菜单 | 下方功能菜单 |

资格被撤销时，会重置订单归属，隐藏商品子页；停留在接单页的用户返回发现页。页面隐藏仅帮助理解，最终权限由后端校验。

| 组件 | 内容、动作、数据来源 |
|---|---|
| 页面文案 | “发现新的协作”；没有旧的首页大横幅、快速邀请按钮或悬浮“＋”发布入口 |
| 服务切换 | “邀请组队 / 邀请护航”，分别对应 `hourly / escort` |
| 游戏切换 | 全部游戏、三角洲、无畏契约、英雄联盟；显示游戏 icon；只是浏览商品筛选 |
| 搜索框 | 搜索商品标题、说明、服务成员和游戏；在已加载商品中筛选 |
| 商品目录 | 俱乐部官方商品置顶；个人商品随后展示；`GET /v1/products` |
| 商品卡主标题 | 服务发布者头像/品牌标记 + 名称；官方保留“官方”标签；不再将商品标题作为主标题 |
| 次要信息 | 游戏 icon + 游戏名；护航额外显示任务；组队不再显示重复的“按约定小时提供服务” |
| 状态 | 官方显示“随机分配”；个人显示“接单中”或“服务中 · 可预约” |

“随机分配”是当前官方卡文案；实际业务为付款后进入公共池，由符合条件的成员抢单或后台派单，没有实现随机算法自动派单。个人忙碌或手动暂停接单不让商品自动下架，仍可预约；实际接受邀请需在线接单意愿开启且无未完成参与订单。

### 购买与多份邀约

流程：商品卡 → 商品详情 → **立即邀约** → 确认订单 → 提交订单 → 支付面板 → 订单详情。

| 输入/展示 | 当前规则 |
|---|---|
| 游戏、类型、发布者、价格 | 从选中商品带入；买家没有自定义定价入口 |
| 区服 | 从该游戏的区服目录中选择 |
| 每份时长 | 仅组队，整数 1～8 小时，字段 `quantity` |
| 购买份数 | 两类服务都支持整数 1～99，字段 `copies`，默认 1 |
| 护航任务 | 只读展示商品约定；每份 `quantity=1` |
| 总金额 | `单价 × 每份时长/任务数量 × copies`，整数分计算 |
| 组队履约 | `quantity × copies` 小时；例如 `1小时 ×3份，共3小时` |
| 护航履约 | 购买 N 份意味着完成 N 份约定任务，提交验收时需确认全部完成 |
| 订单数 | 一次提交只创建一笔订单，不拆成 N 个订单 |
| 支付模式 | 验收环境模拟付款；普通 HTTP 模式只请求已配置渠道，不把失败显示为成功 |

核心请求 `POST /v1/orders`，随后验收支付为 `POST /v1/acceptance/orders/{id}/pay`；正式支付预留 `POST /v1/orders/{id}/payment-attempts`。

### 接单 tab

| 组件 | 当前规则 |
|---|---|
| 范围切换 | “公共单 / 私有单”；已移除原游戏/服务大卡切换和过滤开关、筛选弹窗 |
| 公共单 | 官方商品产生的已付款待接订单；无指定人；自动按本人游戏×服务类型入驻结果筛选，排除自己下的单和售后冻结单 |
| 私有单 | 老板购买本人个人商品、指定本人接单的已付款待接订单；不展示其他人的指定单 |
| 卡片顶部 | 游戏标识、游戏名、组队/护航类型 |
| 履约主信息 | `1小时 ×N` 或 `约定任务 ×N`；旧订单按 `×1` 展示 |
| 服务信息行 | 下单用户名称 + 公共单/指定我接单 |
| 游戏信息行 | 区服 + 时长组队/任务护航；卡片不显示“验收样例”字样 |
| 收入 | 整笔订单的 `earnings`，文案“预计收入”；有副手时最终个人份额还需按人数分配 |
| 按钮 | 公共单“立即抢单”；私有单“接受邀请” |
| 成功后 | 自动占用服务容量，状态变为服务中，刷新个人档案、订单和商品卡状态 |

前端过滤函数见 [hall-orders.ts](../../apps/mobile/src/services/hall-orders.ts)。公共数据来自 `GET /v1/orders?scope=hall`，私有单从本人可见订单列表取出；点击卡片抢单实际调用 `POST /v1/orders/{id}/accept`。后端另有“自动取最早可接订单”的 `/v1/orders/grab`，当前列表卡按钮不调用它。

### 我的 tab 与订单详情

| 组件 | 当前能力 |
|---|---|
| 个人区 | 头像字形、名称、介绍；成员显示接单中/服务中开关；开关不是设备在线心跳 |
| 统计 | 全部、进行中、已完成，可进入对应订单状态 |
| 我的订单 | 归属切换仅成员显示；状态栏含全部、进行中、待付款、待接单、待开始、服务中、待确认、已完成、售后；不重复展示“我的订单”标题行 |
| 指定成员信息 | 指定邀约在订单卡和详情透出目标服务成员，避免把指定单当公共单 |
| 我的商品 | 已入驻用户专属；展示本人商品、在售数、上下架、发布；发布表单包含游戏、类型、标题、说明、单价和护航任务 |
| 我要入驻 | 位于下方功能菜单；按三个游戏×两类服务分别申请与查看审核/考核进展 |
| 切换体验账号 | 仅 Mock / 内部验收；普通 HTTP 模式使用退出登录；底部菜单保留相应操作 |
| 帮助与客服 | 服务说明、如何售后、现有客服渠道提示；未接入实时客服聊天 |
| 收入 | 从参与订单查看本人份额和记账/转账状态；没有独立报酬底部 tab |

订单详情按归属、状态和售后状态显示操作：付款、取消、接受邀请、开始服务、添加/移除护航副手、提交完成、用户确认、申请售后。已记账订单暂不接受新退款。用户退款原因选填，无最小字数；金额仍需有效且不超过订单金额。

组队倒计时每秒本地更新，但能否完成由服务端时钟决定。护航开始前可添加副手，最多包含负责人在内 8 人；开始后名单锁定。预计整单收入、个人预计份额、`credited` 已记账、`paid` 已转账是不同概念。

## 管理后台：页面与操作

后台统一位于 `/admin/`，使用 hash 页面。登录页先调用 `/v1/auth/session` 恢复会话；未登录展示账号密码表单。当前只使用最高权限账号 `norman_app_manager`，不显示员工演示身份或切换入口。

| 地址 | 页面和主要 UI | 操作与接口 |
|---|---|---|
| `#dashboard` | 今日实收、今日订单、在线/可接单成员、售后待办、7 日趋势、游戏分布、最新订单、工作动态、入驻处理快捷入口 | `/v1/admin/dashboard`，关联订单、成员与申请；图表为 SVG/CSS，本地展示 |
| `#orders` | 状态汇总、订单状态 tab、搜索、服务类型/游戏筛选、表格、详情抽屉、8 条/页的前端分页 | 查询订单；派单/改派、取消未支付单、CSV 导出 |
| `#players` | 已认证成员、擅长游戏、按游戏×类型入驻标签、档案价、评分/历史单量、接单状态 | 管理员调整档案价和接单意愿；`PATCH /v1/admin/players/{id}` |
| `#customers` | 全部注册用户，包括未下单者；普通/入驻中/已入驻筛选、累计订单、净支付、最近下单、用户订单抽屉 | `/v1/admin/users`；在用户行打开入驻进展抽屉，审核资料、录分通过、拒绝 |
| `#refunds` | 退款金额/笔数汇总、状态筛选、退款列表、订单详情、审核弹窗 | `review-refund`；审批通过后等待渠道，验收渠道模拟处理 |
| `#audit` | 时间、操作人、动作、关联对象、详情 | 管理员查询 `/v1/admin/audit`，无编辑入口 |

通用 UI：侧边栏折叠及窄屏遮罩、全局搜索、刷新、待办提醒、当前账号信息与退出。工作空间切换卡、侧栏移动端体验推广卡、独立入驻考核/报酬结算/俱乐部设置菜单已移除。旧 `#applications/#settlements/#settings` 分别转到客户、订单、概览。

后台抽屉/弹窗：订单详情、用户订单、入驻进展、考核处理、派单/改派、退款审核、档案价调整、当前管理账号。没有账号切换弹窗；账号信息仅用于查看当前账号和退出。

### UI 与接口存在差异的地方

| 事项 | 真实边界 |
|---|---|
| 员工、封禁、任务问题、用户停用 | 后端已有接口，当前没有独立管理页面；不能根据“没有菜单”判断没实现 |
| 产品价和成员档案价 | 下单读取 `product.price`；成员页改 `service_profile.price` 主要改变档案/发布建议价，不会批量修改已在售商品或历史订单 |
| CSV | 浏览器导出当前已加载、筛选后的订单，含份数；不是服务端全库导出接口；会处理公式前缀 |
| 分页与统计 | 订单表格是已加载数据的前端分页；服务端列表有 500 条上限，客户消费汇总受列表范围影响；概览金额使用数据库聚合 |
| 客服发起售后 | 管理后台现有提示框仍要求原因至少 5 字；用户端和服务端退款原因均选填，这不是数据库限制 |
| 在线/接单 | 某些后台文案仍以 `available` 显示“在线/休息”；可立即接单需同时判断 `busy`，设备是否在线未单独建模 |
| 退款后的待接卡 | 客户端排除 `refunded`；服务端公共池仅排除 pending/processing。部分退款后仍 waiting 的订单，其待接可见性条件尚不完全一致，需要后续统一 |
| 评价和历史完成量 | 档案字段存在，但当前未实现评价提交体系，也未自动维护完整历史评分指标 |

## 刷新、实时同步和本地数据

| 机制 | 当前行为 |
|---|---|
| 普通轮询 | 接单、订单及订单弹层约 10～13 秒；其他用户页、后台约 30～33 秒，完成一次后再计时，随机错峰 |
| 目录缓存 | 游戏和俱乐部规则 5 分钟；手动/完整刷新可重新取 |
| 页面生命周期 | 隐藏页面暂停定时器与状态订阅，回来刷新；切换身份清理上个用户数据，旧请求结果不覆盖新身份 |
| 状态推送 | H5 HTTP/验收使用 `/v1/players/events` 的 SSE；收到 `presence: refresh` 再鉴权读取成员列表，不在推送中直接广播个人数据 |
| 兜底 | SSE 失败或不支持时，每 5 秒刷新成员状态；小程序使用轮询；Mock 监听同源存储变化 |
| 接单池 | 后端单进程内缓存，RDS 才是完整订单来源，和前端本地存储无关 |

Mock 主数据键沿用 `stellar-club:database:v1`，其中 `v1` 是历史存储兼容标识，不能当产品版本号。不同浏览器、不同源和小程序的数据互不自动同步。真实 H5 登录凭据使用 HttpOnly Cookie，不把真实管理 token 保存在 LocalStorage。

| 想修改什么 | 先看哪里 | 需要同步 |
