## 2026-11-02 钱包、人工提现与微信收银台（已同步云端内部验收）

版本保持 **1.0.1，未正式发布**。本节能力已部署至云端内部验收环境，部署记录见文末；没有商户号和服务号资料时不宣称已开通真实收款。

- 成员“我的 → 我的钱包”（`pages/account/wallet`）：独立滚动页面展示可提现、待结算、提现中、累计已付款、收支明细、最近200笔提现。已撤销资格但仍有历史收益的成员保留入口。
- 本人银行卡需填写姓名、银行、卡号，确认处理说明并重新输入登录密码。只做卡号格式/Luhn及填报姓名一致性检查，**未接银行四要素/权威实名**，平台付款前必须核对本人账户。已保存信息仅显示脱敏姓名和尾号；完整卡号、密码只在输入时存在，离页清空。
- 提现按人民币金额输入、转换整数分，1～50000元；服务端再次核验金额、可用余额、密码和幂等请求号。待审核可撤销；银行卡在存在未完成提现时不能变更。网络结果不明时原金额沿用请求号，避免重复申请。
- 模拟收入单独标注，不计入真实余额。纯Mock拒绝保存银行卡/真实提现；服务器验收的模拟收款也不会成为真实余额。旧收入不自动导入新钱包。
- 管理后台新增“钱包提现”，仅管理员/财务可进入；支持搜索、状态筛选、审核、核对账户、进入付款、登记已付款及确认未付款。敏感账户查看、每次资金操作重新验证管理员密码。卡号仅本次弹窗显示，关闭或切换身份清空。
- 微信收银台（`pages/account/wechat-pay?orderId=…`）从订单付款入口进入。HTTP构建先读取服务端渠道状态；未配置直接显示未开通，不拉授权、不扣款。开通后只在微信内H5发起公众号OAuth和JSAPI支付；小程序、外部浏览器不支持这条路径。客户端成功回调仅触发查询，以服务端通知/查单为准；刷新后可恢复已有支付尝试。
- 收款人与提现收款人的银行卡、密码、openid、OAuth code均不写入前端持久缓存；回调URL中的code由服务端立即消费并303跳回不含code的用户页。入口/弹窗沿用暗色、荧光绿和紫色风格。

- 明文姓名、证件、密码、验证码仅用于当前输入，不进持久缓存或URL；证件/姓名接口只返回脱敏值。页面离开清空输入，接口沿用Cookie/CSRF及no-store保护。

## 阅读与版本维护规则

本手册是个人维护用的“目前做了什么、入口在哪、改哪里”的总览。章节中的 **1.0.1** 是产品和功能文档版本，不是 Vue、Spring Boot、Flyway 或构建包的版本。

1. 未正式发布前，前端和后端都保持 **1.0.1**；修 UI、加接口、改数据库、推送 Git、部署验收都不自动升版本。
2. 日常改动更新本手册对应章节，并追加到文末的“1.0.1 开发记录”，记录日期、改动、影响和验证。不要为每次修改建立一个新版本。
3. 正式发布由项目所有者明确确认。届时将三份手册复制到 `docs/releases/1.0.1/`，登记发布日期、源码提交、构建模式和数据库迁移版本，保留为不可覆盖的版本快照。
4. 下一版本号由项目所有者确定。新版本保留独立章节或快照，已发布版本的功能说明不直接改写成新行为。
5. 当前 `package.json`、工作区依赖及 Maven 坐标仍有 `1.0.0` 工程包号；本次仅建立功能版本基线，不修改构建坐标或产物名称。这些工程包号不能用来判断是否正式发布。

本手册按实际源码整理。旧 README、演示说明与早期 API 文档中出现的“快速邀请”“发现页＋号”“接单过滤”“员工 TOTP 登录”等历史描述，不代表当前页面。

### 招募确认与订单

流程：商品卡 **立即招募** → **确认招募** → **提交招募** → 支付面板 → 订单详情。点击卡片直接打开确认表单，不再经过商品详情弹窗。确认页使用紧凑服务摘要和行式表单，保留区服、约定任务/时长、价格、联系电话、微信和备注；标题与合计/提交按钮固定，只有中间表单滚动。

| 输入/展示 | 当前规则 |
|---|---|
| 游戏、类型、发布者、价格 | 从选中商品带入；买家没有自定义定价入口 |
| 区服 | 从该游戏的区服目录中选择 |
| 服务时长 | 仅组队，整数 1～8 小时，字段 `quantity`；不展示购买份数，新单 `copies=1` |
| 购买份数 | 仅护航支持整数 1～99，字段 `copies`，默认 1 |
| 预留联系方式 | 两类订单均提供；联系电话必填（手机或座机），默认从本人短信注册身份带入且可修改；微信与备注不显示“选填”；提交前校验，订单详情向下单人、接单后服务成员展示；公共/待接邀请隐藏 |
| 护航任务 | 只读展示商品约定；每份 `quantity=1` |
| 总金额 | `单价 × 每份时长/任务数量 × copies`，整数分计算 |
| 组队履约 | 新订单按 `quantity` 总小时数履约；旧多份订单仍按 `quantity × copies` 履约，卡片汇总显示总小时数 |
| 护航履约 | 购买 N 份意味着完成 N 份约定任务，提交验收时需确认全部完成 |
| 订单数 | 一次提交只创建一笔订单，不拆成 N 个订单 |
| 支付模式 | 验收环境模拟付款；普通 HTTP 模式只请求已配置渠道，不把失败显示为成功 |

核心请求 `POST /v1/orders`，随后验收支付为 `POST /v1/acceptance/orders/{id}/pay`；正式支付预留 `POST /v1/orders/{id}/payment-attempts`。

### 接单 tab

| 组件 | 当前规则 |
|---|---|
| 范围切换 | “公开招募 / 定向招募”；已移除原游戏/服务大卡切换和过滤开关、筛选弹窗 |
| 公开招募 | 官方商品产生的已付款待接订单；无指定人；自动按本人游戏×服务类型入驻结果筛选，排除自己下的单和售后冻结单 |
| 定向招募 | 老板购买本人个人商品、指定本人接单的已付款待接订单；不展示其他人的指定单 |
| 卡片顶部 | 游戏标识、游戏名、组队/护航类型 |

## 刷新、实时同步和本地数据

| 机制 | 当前行为 |
|---|---|
| 普通轮询 | 接单、订单及订单弹层约 10～13 秒；其他用户页、后台约 30～33 秒，完成一次后再计时，随机错峰 |
| 目录缓存 | 游戏和俱乐部规则 5 分钟；手动/完整刷新可重新取 |
| 页面生命周期 | 隐藏页面暂停定时器与状态订阅，回来刷新；切换身份清理上个用户数据，旧请求结果不覆盖新身份 |
| 状态推送 | H5 HTTP/验收使用 `/v1/players/events` 的 SSE；收到 `presence: refresh` 再鉴权读取成员列表，不在推送中直接广播个人数据 |
| 兜底 | SSE 失败或不支持时，每 5 秒刷新成员状态；小程序使用轮询；Mock 监听同源存储变化 |
| 接单池 | 后端单进程内缓存，RDS 才是完整订单来源，和前端本地存储无关 |

Mock 主数据键沿用 `stellar-club:database:v1`，其中 `v1` 是历史存储兼容标识，不能当产品版本号。不同浏览器、不同源和小程序的数据互不自动同步。真实 H5 登录凭据使用 HttpOnly Cookie，不把真实管理 token 保存在 LocalStorage。

- 用户端 H5、管理后台共用 `createHttpTransport`；H5 使用 Cookie/CSRF，不把真实会话 token 放入 LocalStorage。请求包含对应 user/staff audience，超时15秒，禁止浏览器自动跟随接口重定向，设置 no-store。来源或重定向配置错误会报错，不报告登录或支付成功。

- 小程序仍使用 `uni.request` 和 Bearer，沿用 PATCH 的受限方法覆盖；共享不依赖 URL 全局的地址校验，真实环境必须配置合法 HTTPS API 域名。小程序平台请求重定向行为不等同于 H5 的 fetch redirect 策略，服务端接口和网关必须避免重定向、不得将 Bearer 转发到第三方。
